# Scaling notes

One line per task: **what would break first at 100,000 users.** Recorded, not
fixed. The point is that the choice was seen, not that it was solved.

| Task | What breaks first at 100,000 users |
|---|---|
| Stage 1.1 — `app_config` version row | Nothing in the table itself: one row, read once per app start. What breaks is the **download link** — `latest_apk_url` points at a single host serving a ~70 MB file, so a release day is 100,000 × 70 MB of egress from whatever is behind that URL. The row is fine; the thing it points at is not. |
| Stage 1.1 — signed release APK | Now 43 MB after dropping the emulator architectures. At 100,000 users the problem is not the build, it is that **every one of them downloads 43 MB over mobile data from one host** on each native release. Per-architecture splits would halve it again (an arm64 phone does not need the armeabi-v7a copy), and minification would take most of the remaining 29 MB of dex. Both are the same fix at 10 users as at 100,000. |
| Stage 1.1 — minification | R8 cut the dex from 29.4 MB to 8.9 MB, and with it the readability of every crash report: a stack trace is meaningless without that build's `mapping.txt`. At 10 captains you can keep the file in a folder. At 100,000 users across many versions, "which build was this phone on, and where is its mapping file" becomes a thing someone has to run. The version row already records what a phone is on; nothing yet records where its mapping went. |
| Stage 1.2 — founder-code sign-in | Test phone numbers are stored one-by-one in the Supabase dashboard, by hand. That is fine for ten captains and impossible at a thousand: there is no bulk import, no expiry per number, and every entry is a standing back door that someone has to remember to remove. It does not scale and is not meant to — it exists until DLT registration clears. What must not be built on top of it is anything that assumes a code is permanent. |
| Stage 2.7 — lock-screen accept | The handler now calls accept_job directly, so every tap is one round trip with no local read. That is the right shape at any size. What breaks first is the ping that precedes it: notify-dispatch reads every pending captain's push tokens and posts them to Expo in a single request per job. At 100,000 users that is fine per job and unbounded in aggregate — nothing batches or rate-limits across jobs, and Expo's push API has its own limits. Record, do not fix. |
| Stage 2.5 — sending accept | Each captain on a bad signal retries `accept_job` every 5 s for up to 90 s: at most 18 calls per offer per phone, a constant. At 100,000 users the first thing to break is not the retries but the 90-second window itself, which exists only on the phone — nothing on the server closes an offer, so an offer lives until the job is taken or the day ends. Server-side rounds (TECH_ARCHITECTURE "Timeout") are the fix; the client constant should then be read from there. |
| Stage 2.9 — append-only walk | Nothing here grows with users; it is per phone. What breaks first is a very long walk: recovery reads every point key back with `getAllKeys` + `multiGet`, so a two-hour walk is ~7,200 keys read in one go on a cheap phone. That only happens on a crash restore and a field is walked in minutes, so record it, do not fix it. If it ever bites, batch points into fixed chunks of ~100 per key. |
| Stage 2.8 — restore and back | Per phone, so users do not change it. What breaks first is the shape of the app: one `screen` value and a hand-written back table work for ten screens, and every new screen must be added to `backFrom` and `restoreScreen` or it silently exits on back and reopens at home. Past ~20 screens, or the first nested flow beyond booking, move to a navigation library that owns history and state restoration. |
| Stage 3.1 — nightly backup | A full logical dump of the whole database every night. At 100,000 users the database is gigabytes: the dump outgrows the job's 15-minute timeout, and 30 copies are far past GitHub's 500 MB of free artifact storage. That is the point to pay for Supabase's own point-in-time backups, not to tune this. |
| Stage 3.2 — switches | One global row. Across many districts a switch has to differ per region (auto-dispatch on in Fazilka, off in a new district), so `auto_dispatch` and `loud_ping` will want a `region_id`. Additive when it comes: a per-region row that overrides the global one. |
| Stage 3.3 — metrics views | Plain views recomputed on every open, scanning all jobs and fields. Fine at thousands of rows; at 100,000 users `farmer_return_60d` (a subquery per farmer) is the slow one. Make it a materialized view refreshed nightly. |
| Stage 3.4 — costs | The first free limit is Supabase's 5 GB egress at around 100 captains, because sync re-downloads every field and job on every pass; the second is Expo Update's 1,000 monthly users. Incremental sync fixes the first; the second is a plan change or self-hosted updates. |
| Incremental sync | A pass now costs what changed, not what exists, so egress no longer grows with history. What breaks first at 100,000 users is the 5-minute overlap: every pass re-reads every row touched in the last five minutes, and in a busy district at harvest that window holds many offers moving per job. Narrow the overlap, or move to a change feed, when a pass measurably re-reads more than it gets new. |
| Stage 4.1/4.2 — founder dispatch | One person matching every job by hand. That is the bottleneck long before any table is: at a few hundred jobs a day in harvest, one phone cannot keep up, and that is the day automatic dispatch goes on. The founder job list is capped at 50 and has no region filter; per-district staff need both. |
